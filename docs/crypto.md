# Crypto in the workbench

The workbench runs m33mu's own crypto models in the browser: the on-chip crypto engines of each SoC and the secure elements m33mu simulates on its I²C/SPI buses. Nothing is reimplemented in JavaScript; the WASM build is the same C (and Rust) code the CLI runs.

## Build

Both are optional and reported by the worker's `features` operation (and in the Capabilities list):

| Feature | Needs | CMake (lab) |
|---|---|---|
| `wolfcrypt`: on-chip engines, TA100 | a wolfSSL source tree; wolfCrypt is compiled for WASM from it with `m33mu/cmake/wasm/wolfssl/user_settings.h`, never vendored | `-DM33MU_WOLFSSL_SRC=/path/to/wolfssl` |
| `rustSecureElements`: ATECC608A, SE050, STSAFE-A120, TROPIC01 | cargo and `rustup target add wasm32-unknown-emscripten` (crates from `m33mu/third_party/wolfssl-simulators`) | `-DM33MU_WASM_RUST_SE=ON` |

Without them the build still works: crypto registers read as the CLI without wolfSSL, and secure-element parts stay silent on the bus with a diagnostic. wolfCrypt's RNG is seeded from `getentropy()` (the browser's `crypto.getRandomValues`).

## On-chip engines

Whatever the target's MMIO model implements, as in the CLI: STM32 HASH/AES/SAES/PKA/RNG, LPC55S69 HASHCRYPT and CASPER, nRF5340 CryptoCell, the MCX/RT700/RW612 secure blocks. Firmware simply uses them. Verified in the browser worker by `scripts/test-web-crypto.mjs` with m33mu's test firmware (HASHCRYPT SHA-256/AES-ECB, CASPER, CryptoCell, U585 PKA ECDSA P-256 sign and verify).

## Secure elements on the bench

| Part | m33mu model | Bus | Header |
|---|---|---|---|
| ATECC608A | `atecc608` (Rust) | SPI | VCC GND CS SCK MOSI MISO |
| TA100 | `ta100` (C, wolfCrypt) | SPI | VCC GND CS SCK MOSI MISO |
| TROPIC01 | `tropic01` (Rust) | SPI | VCC GND CS SCK MOSI MISO |
| SE050 | `se050` (Rust), address 0x48 | I²C | VCC GND SCL SDA |
| STSAFE-A120 | `stsafe` (Rust), address 0x20 | I²C | VCC GND SCL SDA |

When the bench starts, each secure element's bus is derived from the header pads its lines reach (the pad's alternate functions, `sim/buses.ts` `H563_AF`) and its chip select from the GPIO pad wired to CS; the worker attaches the model with the CLI device syntax (`atecc608:SPI1:cs=PD14`, `se050:I2C1:addr=48`, see `mm_web_attach_device`). From then on:

- The bus layer still owns the wiring: a part answers only with VCC/GND powered (≥ 1.6 V) and every bus line connected, I²C lines must be pulled up, and two devices at one address clash, as for the JavaScript devices (`buses.md`).
- If the part is wired and attached, the transfer is handed to m33mu's model, which answers the protocol (APDUs, CRCs, command sets). Otherwise the bus layer answers as an absent device would: I²C NACK, SPI MISO floating.
- Sniffers and the bus log show each transfer and which model answered; SPI MISO bytes and I²C read data produced by a model are not shown (the bus layer only sees the request).
- Each bench start attaches fresh models: device state (keys, counters, NV) lasts while the bench runs. NV files are not persisted.

Not available in the browser: the TPM 2.0 model (needs libtpms) and the IoT SAFE modem (it is a UART backend, not yet bridged to the lab's UART routing).

Example: `h563-secure-elements` (gallery) runs m33mu's secure element suite (`tests/firmware/test-stm32h563-web-se`) against all three parts on NUCLEO-H563ZI header pins. Tests: `scripts/test-web-secure-elements.mjs` (bench wiring, unpowered part NACKs), `tests/sim/buses.test.ts` (spec derivation and hand-off), Chromium example check.
